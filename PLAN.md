# ZX Spectrum Next Graphics Converter — план реализации

## Контекст

Делаем с нуля Windows-приложение, которое конвертирует PNG/BMP/JPG в нативные для ZX Spectrum Next данные тайлов/спрайтов/Layer2, даёт руками редактировать пиксели и палитры, и экспортирует бинарники по 8КБ плюс ASM-карту адресов для Z80-программы. Рабочая директория пустая — проект с нуля. Требования взяты из вашего техдока плюс факты по железу, которые я перепроверил напрямую по исходникам FPGA-ядра ZX Next (`tilemap.vhd`, `sprites.vhd`) и регистровой документации, а не только по вторичным источникам. Вы явно попросили: сначала UI (можно с заглушками), логика — потом, приложение разбито на понятные панели.

Подтверждённые ограничения железа, определяющие дизайн:
- Аппаратный тайлмап — только 4bpp (доказано прямо в RTL). Категория "tile/8bpp" в приложении — это не для этого движка, а 8x8-куски, нарезанные из 8bpp Layer2-графики, для собственного софтверного тайлмапа программиста.
- 4bpp спрайты/тайлы: итоговый индекс палитры = `paletteOffset*16 + pixelNibble` (подтверждено в RTL) — то есть 16 смежных 16-цветных окон в одном банке палитры, один общий индекс прозрачности на все 16.
- Полноэкранные режимы Layer2: 256x192x8, 320x256x8 и 640x256x4 (16 цветов) — все три поддерживаются нарезчиком атласа как пресеты "без сетки, одно целое изображение".
- Формат хранения палитры: файл 512 байт (256 байт RRRGGGBB + 256 байт бита синего) — это точное отражение того, как реально пишется аппаратный регистр (nextreg 0x44).

## Стек (зафиксировано, уже согласовано с вами)

C# / .NET 8, WPF (не Avalonia — инструмент только под Windows, побеждает зрелость дизайнера форм). CommunityToolkit.Mvvm для MVVM (генерируемые `[ObservableProperty]`/`[RelayCommand]`, `IMessenger` для живого обновления между панелями). Без библиотеки докинга (AvalonDock и т.п.) — описанный layout это фиксированные 2-3 панели, а не свободная IDE-раскладка; делаем руками через `Grid`+`GridSplitter`. Декодирование изображений — через встроенный в WPF `BitmapDecoder`/`FormatConvertedBitmap` (без лишних зависимостей, PNG/BMP/JPG из коробки) за интерфейсом `IImageDecoder`, чтобы `Core` не зависел от WPF. Весь текст внутри приложения — на английском.

## Доменная модель

```
readonly struct NextColor { byte R3,G3,B3; }  // 3 бита на канал, 512 значений всего
  .ToRegByteRRRGGGBB() / .ToBlueLsbBit()        // точно соответствует формату двух записей nextreg 0x44
  .ToDisplayRgb24()                             // расширение до 8 бит (bit-replicate) для превью на экране

enum AssetCategory { Sprite4bpp, Sprite8bpp, Tile4bpp, Tile8bpp }

// 4bpp: один PaletteBank на категорию (банк Sprite4bpp, банк Tile4bpp), до 16 слотов NextPalette
// по 16 цветов, один общий индекс прозрачности на весь банк.
class PaletteBank { AssetCategory Category; int SharedTransparentIndex; List<NextPalette> Slots /*0..16*/; }
class NextPalette { NextColor[] Colors; }        // длина 16 (4bpp-слот) или до 256 (плоская 8bpp)

// 8bpp: НЕСКОЛЬКО именованных плоских палитр на категорию, по одной на конечную папку дерева
// (ваш выбор от 2026-08-19: "несколько палитр внутри категории"). Каждая папка под sprite/8bpp/images
// или tile/8bpp/images, напрямую содержащая изображения, владеет одной палитрой (до 256 цветов),
// построенной через median-cut по изображениям этой папки. Новая подпапка = новая независимая
// 8bpp-палитра; ассеты в ней не могут ссылаться на цвета вне палитры своей папки.

abstract class GraphicsAssetBase
{
    Guid Id; string Name;                 // имя файла без расширения -> становится меткой в ASM
    AssetCategory Category; byte[] PackedPixelData;  // ВСЕГДА источник истины (см. раздел "Хранение")
    Guid? SourceImageId; AtlasPosition? OriginInSource;
    Guid PaletteRef;                       // 4bpp -> id слота PaletteBank; 8bpp -> id палитры своей папки
}
class SpriteAsset : GraphicsAssetBase { }   // всегда 16x16
class TileAsset : GraphicsAssetBase { }     // всегда 8x8
class Layer2Image { Guid Id; string Name; Layer2Mode Mode /*256x192x8|320x256x8|640x256x4*/; byte[] PackedPixelData; NextPalette Palette; }
```

## Модель хранения (файл проекта)

**Поправка к наивной идее "при загрузке всё пересчитывать из исходника"**: поскольку пользователь может руками редактировать отдельные пиксели (ограничено палитрой ассета) и цвета в палитре, `PackedPixelData` перестаёт быть чистой функцией от исходника+настроек квантизации после любой ручной правки — пересчёт из исходника при загрузке тихо уничтожил бы ручную работу. Поэтому:

- Папка проекта на диске: `project.json` (манифест: структура дерева, ссылки на исходные изображения, банки палитр/плоские палитры, метаданные по каждому ассету) + `sources/` (копии импортированных исходных изображений, чтобы проект был переносимым) + `assets/<assetId>.bin` (реальные `PackedPixelData` каждого ассета, хранятся как есть — настоящий источник истины, переживает ручные правки).
- Повторный запуск квантизации/дизеринга на ассете — явное действие пользователя ("реквантовать этот тайл/папку"), никогда не побочный эффект открытия проекта.

## Квантизация и дизеринг (`Core/Quantization`)

- Метрика расстояния: **взвешенное евклидово расстояние redmean** (стандартная эвристика "умного" подбора ближайшего цвета, дёшево, без перевода в другое цветовое пространство — так делает большинство ретро-инструментов для "умного усреднения"). Грубая предпосчитанная LUT (округление исходного RGB до 5 бит на канал = 32768 корзин, ближайший из 512 посчитан один раз) даёт O(1) на пиксель.
- Дизеринг, три реальных алгоритма за интерфейсом `IDitherer`: **None**, **Ordered (Bayer 4x4)**, **Floyd–Steinberg**. Диффузия ошибки идёт по *всему исходному изображению* до нарезки на атлас, а не по отдельным тайлам — иначе на границах тайлов будут видны швы.
- Построение плоской 8bpp-палитры: **median-cut** по гистограмме пикселей папки, затем каждый центр кластера привязывается к ближайшему из 512 аппаратных цветов (произвольные центры кластеров не представимы в железе).
- Порядок конвейера: сначала дизеринг/подбор каждого пикселя к ближайшему из 512 цветов Next (не зависит от категории), затем полученный набор цветов тайла идёт либо в алгоритм распределения 4bpp-палитр (см. ниже), либо в поиск индекса по плоской палитре папки для 8bpp.

## Алгоритм распределения 4bpp-палитр (`PaletteAllocator`)

Обрабатываем ассеты по одному, в порядке дерева, относительно `PaletteBank` их категории (до 16 слотов, 15 цветов доступно на слот, так как 1 индекс зарезервирован под общий прозрачный цвет):

1. **Совпадение по подмножеству**: если непрозрачные цвета тайла — подмножество цветов существующего слота, назначаем этот слот как есть (first-fit — просто и достаточно для первой версии).
2. **Слияние**: иначе ищем существующий слот, объединение с которым требует *меньше всего новых* цветов и укладывается в 15; добавляем новые цвета тайла в свободные индексы этого слота (уже назначенный цвет никогда не переезжает на другой индекс — иначе сломаются ранее привязанные тайлы).
3. **Новый слот**: иначе, если слотов меньше 16, создаём новый.
4. **Переполнение**: иначе помечаем ассет как неразмещённый и продолжаем сканирование дальше (чтобы пользователь увидел сразу весь список проблемных, а не по одному). Переполнение предлагает два варианта из техдока: реквантовать всю папку на меньшее число цветов, либо уменьшить цвета только у проблемных ассетов, затем повторить распределение.

Индекс прозрачности — настройка на уровне `PaletteBank`, фиксируется, как только в банке появился хоть один ассет (сменить его позже можно только явной операцией "сменить индекс прозрачности и пересчитать всё").

## Экспорт (`Core/Export`)

Поправка по вашим ответам от 2026-08-19 (в ASM-карте нет фиксированного адреса загрузки — вместо него смещение ассета внутри его 8КБ-слота):

- `BinaryChunker`: упаковывает ассеты последовательно в 8КБ (8192 байта) чанки **отдельно по каждой экспортируемой папке** (ассет никогда не разрезается между чанками — это безопасно, так как самый крупный ассет, 8bpp-спрайт 256 байт, ничтожно мал относительно 8КБ). Для каждого ассета получаем `(индекс_слота, смещение_в_слоте)`.
- **Нумерация слотов начинается заново с 0 в каждой экспортируемой папке** (по вашему ответу: "каждая папка свои счетчик") — то есть `sprite/4bpp`, `sprite/8bpp`, `tile/4bpp`, `tile/8bpp` (и отдельная подпапка, если экспортируется отдельно) каждая получает свою последовательность `slot_000, slot_001, ...` и свои бинарные файлы, названные по пути в дереве с числовым суффиксом при переполнении одного чанка.
- `AsmMapGenerator` формирует на каждую экспортируемую папку блок констант `slot_nnn: equ <n>`, затем по одной метке на ассет (имя = имя файла-источника):
  ```
  tile_name:
      db slot_003      ; в каком 8КБ-банке этой папки лежит чанк 3
      dw <offset>       ; смещение данных этого ассета внутри чанка, от 0
  ```
- `ExportService` — оркестрация: выбранная область → чанкинг → генерация ASM → запись `.bin`/`.asm` в выбранную папку. Чистая детерминированная функция, легко тестируется golden-сравнением.

## Панели UI и связь с MVVM

Фиксированный layout `Grid`+`GridSplitter`: левая колонка — `ProjectTreeView` (собственное виртуальное дерево приложения — `sprite/4bpp/images`, `sprite/8bpp/images`, `tile/4bpp/images`, `tile/8bpp/images`, создаваемые пользователем подпапки для группировки 8bpp-палитр); правая колонка делится по вертикали на `ImageViewerView`+`PaletteStripView` (выбранный ассет + его палитра) и `PixelEditorView` (инструмент рисования, ограниченный палитрой ассета). Нарезчик атласа — модальное окно, открывается автоматически при перетаскивании изображения большего размера в папку категории (пресет размера ячейки берётся из целевой категории: 8x8/16x16 для тайлов/спрайтов, 256x192/320x256/640x256 для полноэкранных Layer2, везде настраиваемые отступы слева/сверху + один общий параметр расстояния между ячейками, по умолчанию 0). Правка цвета в палитре рассылает `PaletteChangedMessage` через `IMessenger`; все отрендеренные вьюхи, привязанные к этой палитре, перерисовывают свой `WriteableBitmap` — сами `PackedPixelData` от правки палитры не меняются, меняется только отображаемый цвет. Простой стек отмены покрывает правки палитры и рисование пикселей.

## Поэтапная разработка (сначала UI, как вы просили)

1. **Каркас** — созданы solution/проекты, DI, фиксированный layout панелей с фейковыми данными дерева и заглушкой-картинкой. *Готово, когда:* приложение запускается, панели видны, выбор фейкового узла дерева меняет содержимое правой панели.
2. **Реальный импорт, без конвертации** — `SourceImage`/`IImageDecoder`/`WpfImageDecoder`, drag-and-drop из проводника в папку категории, превью в исходном RGB (квантизации ещё нет), базовое New/Save/Open проекта, сохраняющее дерево + ссылки на исходники. *Готово, когда:* перетащили PNG в папку, видим узел в дереве, видим картинку как есть, перезагрузили проект — всё осталось.
3. **Нарезчик атласа** — пресеты размера ячейки, поля отступов/расстояния, живой оверлей сетки, авто-открытие при перетаскивании крупного изображения, на выходе отдельные (пока не квантованные) узлы тайлов/спрайтов. *Готово, когда:* картинка 128x128, брошенная в `tile/4bpp`, даёт 16x16 отдельных узлов-тайлов 8x8.
4. **Квантизация + дизеринг + плоские 8bpp-палитры** — `Rgba32ToNext512Matcher`, все три `IDitherer`, `FlatPaletteQuantizer` по папкам для 8bpp-категорий, реальный рендер `WriteableBitmap` из упакованных байт (подтверждает правило "рендер по требованию, упакованные байты — истина" на практике). *Готово, когда:* 8bpp-тайл показывает реально квантованное под Next превью, полоска палитры показывает построенную палитру папки, смена режима дизеринга меняет превью вживую.
5. **Распределение 4bpp-палитр** — `PaletteBank`/`PaletteAllocator` точно по алгоритму выше, UI переполнения с двумя вариантами исправления. Здесь максимум юнит-тестов (совпадение по подмножеству, приоритет слияния, стабильность индекса прозрачности, срабатывание переполнения). *Готово, когда:* несколько 4bpp-тайлов с пересекающимися/непересекающимися цветами корректно группируются в ≤16 слотов, видно на панели банка палитр, а необходимость >16 палитр вызывает подсказку о переполнении.
6. **Редактирование пикселей и палитры с живым обновлением** — `PixelGridCanvas`, ограниченный назначенной палитрой, правка цвета в палитре рассылает `PaletteChangedMessage` всем зависимым вьюхам, стек отмены. *Готово, когда:* правка одного цвета в палитре мгновенно перерисовывает все тайлы/спрайты, использующие эту палитру, а байты `PackedPixelData` не меняются.
7. **Экспорт/генерация ASM** — `BinaryChunker` (нумерация слотов по папкам) + `AsmMapGenerator` (метки со смещением на ассет) + `ExportView`. *Готово, когда:* экспорт проекта, вынуждающий ≥2 чанка в одной папке, даёт корректно нарезанные `.bin`-файлы (≤8192 байт каждый) и `.asm`-файл, где константы `slot_nnn` и пары `db slot_nnn`/`dw <offset>` на каждый ассет точно совпадают с вручную посчитанными ожиданиями на маленьком тестовом проекте.
